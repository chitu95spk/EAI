Facts worth carrying forward:

- oneDNN moved from `oneapi-src/oneDNN` to **`uxlfoundation/oneDNN`**. The old URL redirects; the script uses the canonical one.
- Pinned to **`v3.12.4`** (`v3.13.1` was newest at the time; the more-patched line is pinned instead). Bumping the version can change kernel selection and therefore training numerics, which breaks the determinism requirement in plan section 7.1. Bump deliberately, re-run the gradient check, record it in the plan.
- **Correction to an earlier draft of this card:** the ISA is *not* pinned with a build flag. oneDNN compiles every kernel and dispatches at run time. To pin it for a reproducibility check, set the environment variable `ONEDNN_MAX_CPU_ISA=AVX2`. The 1240P has AVX2 and no AVX-512, so it selects AVX2 unaided.
- Built with `DNNL_CPU_RUNTIME=OMP` for this spike. **SA2 is expected to rebuild with `-Runtime THREADPOOL`**, because pinning the optimizer step to the four P-cores (plan section 1.3) requires the application to own the thread pool. Flagged in the README so it is not forgotten.
- `DNNL_GPU_RUNTIME=NONE` — the SYCL/Iris Xe path is deferred (plan section 16) and would drag in a DPC++ toolchain.
- `dnnl.dll` is **engineering-PC only**. If it ever appears in a line deployment package, the build boundary has broken.

## Steps

1. Run `ThirdParty\oneDNN\download-onednn.ps1`. Confirm `install\include\oneapi\dnnl\dnnl.hpp`, `install\lib\dnnl.lib` and `install\onednn-build-manifest.json` exist.
2. Create `BeeAiSpike` as a console exe, x64, `stdcpp17`, v143, with `IncludePath` pointing at `ThirdParty\oneDNN\install\include` and `LibraryPath` at `...\install\lib`, linking `dnnl.lib`, plus a post-build copy of `install\bin\dnnl.dll` next to the exe. It is deliberately outside `BeeAiRuntime` — this is scaffolding, not product code.
3. Build one block: `conv3x3(3->16, stride 1) -> batch_norm -> SiLU`, forward and backward, using oneDNN primitives directly:
   - forward: `convolution_forward`, `batch_normalization_forward` (training mode, so it produces mean/variance), `eltwise_forward` with the swish algorithm;
   - backward: `eltwise_backward`, `batch_normalization_backward`, `convolution_backward_data`, `convolution_backward_weights`.
4. Add a plain SGD update over the conv weights, bias, and the BN scale/shift.
5. Fit a synthetic target: fixed random input batch, fixed random target tensor, MSE loss. **Convergence check:** loss must drop by at least 100x within 200 iterations. If it does not, the wiring is wrong — most likely a memory-format mismatch, which is the classic oneDNN trap. Use `memory::format_tag::any` for primitive descriptors and let oneDNN pick, then insert `reorder` where the chosen format differs from what you hold.
6. **Gradient check**: pick 20 random weight elements, compare the analytic gradient against a central-difference numerical gradient. Relative error must be under 1e-4. Without this the loss can fall for the wrong reasons.
7. Measure, with the thermal discipline from plan section 1.3:
   - warm up 60 s;
   - then run **30 minutes continuously**;
   - report iterations/s over the **last 5 minutes only**, plus peak RSS;
   - repeat with the optimizer step pinned to P-cores (affinity mask for the 4 P-cores) versus left to the scheduler, and report both. This directly validates the P/E claim in plan section 1.3.
8. Write the numbers into plan section 1.2 and into the card result.

## Notes

- The single most common way this spike fails is a silent memory-format mismatch: the primitive wants `nChw8c`, you hand it `nchw`, and it trains slowly or wrongly with no error. Query the primitive descriptor for its preferred format and reorder into it.
- BN in training mode has different primitive flags than in inference. Getting this wrong makes the loss plateau rather than error out.
- Keep the spike ugly and short. It is evidence, not architecture, and SA2 will not reuse a line of it.
