# Card SA0.3 — Training throughput probe (HARD GATE)

Plan: `docs/AiPlan/SegAI-V2-BeeLearn-Plan.md`. **Read plan §1 Contract + §6.3 (BeeDet-R topology) + this file. Nothing else.**

Depends on SA0.2 (oneDNN wired and gradient-checked). Build pre-authorized (plan §1.2).

## Why this card exists

This is the gate that decides whether the whole plan is buildable. If a training epoch is too slow on the target machine, no amount of good architecture downstream rescues it. Answer it with a measurement now, before SA1-SA4 spend 25 weeks.

## Two stages

| Stage | Machine | Purpose |
|---|---|---|
| **A** | **i7-1360P** — this dev box: Raptor Lake-P, 12 cores (4P+8E) / 16 threads, 28 W base, 16 GB, AVX2, Iris Xe 96 EU | Validate the harness and methodology, get the baseline, exercise the P/E affinity comparison. **Not the gate.** |
| **B** | **i5-1240P** — the engineering PC: Alder Lake-P, 12 cores (4P+8E) / 16 threads, 28 W base, AVX2, Iris Xe 80 EU | **The gate.** Same numbers, same procedure, on the machine that will actually train. |

Run A first. Only ship/configure the 1240P once A passes with margin.

### Translating A into a prediction for B

The two parts share the core layout (4P+8E/16T), the power class (28 W base) and the ISA (**AVX2, no AVX-512, no AMX** — FP32 training on both). They differ mainly in clocks and L2: the 1360P is a generation newer and clocks higher.

**Expect the 1240P to land 15-25% slower than the 1360P on sustained CPU training.**

Therefore: **Stage A must beat the Stage B budget by ≥ 25%**, not merely meet it. A Stage-A result that only just passes predicts a Stage-B failure. Treat that as an early warning and re-scope before buying or configuring the target machine — that is the entire point of running A first.

Record both machines' actual sustained numbers; the observed A→B ratio becomes the scaling factor used for the rest of the project.

## Method — microbenchmark and roll-up, not a full network

SA0.3 runs **before** SA2 builds the graph and autograd tape, so hand-wiring a complete network here would duplicate work that SA2 will throw away. Instead:

1. Measure forward+backward time for each distinct `(op, input shape, channels)` tuple in the BeeDet-R-N inventory below.
2. Multiply each by its occurrence count and sum → predicted per-image time.
3. Add a **20% locality allowance** for inter-layer memory effects a microbenchmark cannot see.
4. Epoch time = per-image × 2000 images.

State clearly in the result that this is a roll-up estimate. The full-network measurement happens in SA4.4 when the real graph exists; if the two disagree by more than 30%, that discrepancy is itself a finding worth recording.

## BeeDet-R-N inventory to measure (input 320×320, K=4 classes)

Approximate widths — exact values are tuned in SA4.1. The probe needs the right **op mix and order of magnitude**, not the final model.

Inverted-residual (IR) block = `1×1 expand ×4` → `3×3 depthwise` → `1×1 project`, each followed by BN, SiLU on the first two, residual add when shapes match.

| Stage | Op | Resolution | Ch in→out | Count |
|---|---|---|---|---|
| Stem | conv3×3 s2 + BN + SiLU | 320→160 | 3→16 | 1 |
| S1 | IR block s2 | 160→80 | 16→24 | 1 |
| S2 | IR block (first s2) | 80→40 | 24→48 | 2 |
| S3 | IR block (first s2) | 40→20 | 48→96 | 3 |
| S4 | IR block (first s2) | 20→10 | 96→160 | 2 |
| Neck | conv1×1 lateral | 40, 20, 10 | 48/96/160→64 | 3 |
| Neck | upsample nearest ×2 + add | 20→40, 10→20 | 64 | 2 |
| Neck | conv3×3 depthwise fuse + BN + SiLU | 40, 20, 10 | 64 | 3 |
| Neck | conv3×3 s2 downsample + add (bottom-up) | 40→20, 20→10 | 64 | 2 |
| Head | conv3×3 depthwise + conv1×1 + BN + SiLU | 40, 20, 10 | 64→64 | 6 |
| Head | conv1×1 cls / reg / angle | 40, 20, 10 | 64→4 / 64→4 / 64→2 | 9 |

C3=stride 8 (40×40), C4=stride 16 (20×20), C5=stride 32 (10×10). Batch size 8 for all measurements; also record batch 1 and 16 so SA2 can pick.

## Measurement discipline — non-negotiable

The 28 W base power limit means a long run settles well below its opening speed. Numbers taken in the first minute are worthless.

- Pin the ISA for reproducibility: `ONEDNN_MAX_CPU_ISA=AVX2` (both parts select AVX2 anyway; pinning makes the run repeatable).
- **Warm up 60 s**, then run **30 minutes continuously**, then report **only the last 5 minutes**.
- Sample and record CPU package clock every 30 s for the whole run so the throttle curve is visible, not inferred. Report opening clock, final clock, and the drop.
- Record peak RSS.
- Report both affinity settings:
  - **P-pinned**: optimizer/compute threads restricted to the 4 P-cores (affinity mask covering the first 8 logical processors on both parts — P-cores enumerate first).
  - **Free**: no affinity, left to the Windows scheduler.
  This directly tests the P/E claim in plan §2.1. If P-pinning does not help, that claim is wrong and the plan must be corrected.
- Also record memory configuration (channels / soldered LPDDR width). Conv training is bandwidth-bound; single-channel halves effective bandwidth.

## Gate

| Outcome | Action |
|---|---|
| Stage B < 4 min/epoch | Proceed. Write the measured numbers into plan §6.3 |
| Stage B within 2× of budget | Proceed with a reduced profile: input 256 instead of 320, or fewer epochs via warm start. Record the choice in the plan |
| Stage B > 2× budget | **STOP and re-scope.** Options: a smaller profile, a discrete-GPU training box, or dropping D2 back to head-only training. This is a user decision, not an implementation detail |

A 100-epoch BeeDet-R-S run at ~10 min/epoch is an overnight job. That is the intended shape and is why training was moved off the production line (D5/D6).
